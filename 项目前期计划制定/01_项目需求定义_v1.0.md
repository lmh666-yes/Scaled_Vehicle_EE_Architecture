## 0. 一句话

**车上三块 MCU 挂在同一条 CAN 总线上，车外一台 PC 和一台手持终端：**

- **ESP32-S3** 管总线、无线、图像（核心层 ≈ VCU + 网关 + T-Box）
- **F407** 管电机与安全（动力域 ≈ MCU 电机控制器）
- **F103** 管配电与保护（电源域 ≈ BMS / PDU）

**控制走有线 CAN，指令走 WiFi，遥测走 LoRa，图像只在停车巡检时开。**

不追求"能跑多快"，追求"坏的情况下还对"。

## 2. 系统构成

### 2.1 节点：车上三块，车外两件

| 节点 | 硬件 | 真车对应 | 职责 | 状态 |
|---|---|---|---|---|
| **核心层** | ESP32-S3-N16R8 | VCU + 网关 + T-Box | 指令解析、仲裁、报文路由、心跳超时、WiFi/LoRa、图像、日志、诊断转发 | ✅ 已有 |
| **动力域** | STM32F407 核心板（VET6 或 ZGT6） | MCU 电机控制器 | 4 路编码器、4 路 PWM、1 kHz 速度环、电压前馈、急停、欠压切断、UDS 服务端 | 🛒 待购 ≈¥45 |
| **电源域** | STM32F103C8T6 核心板 | BMS / PDU | 母线电压电流、硬件比较器、主 MOS、分级上电、SOC | 🛒 待购 ≈¥12 |
| **上位机** | PC + USB-CAN 适配器 | 诊断仪 / 最小版 HIL | Qt 仪表、抓包、注帧、UDS、虚拟第二车、图像显示 | PC 已有，适配器待购 |
| **手持终端** | 天马 ZGT6 带彩屏板 | 诊断仪手持端 / 备份控制器 | 遥测显示、按键控制、LoRa 备份链路 | ✅ 已有 |
| **开发台** | 正点原子探索者 ZET6（带 CAN 收发器/TFT/MPU6050/按键） | 工程样件 | **不上车**，桌面验证代码与故障注入 | ✅ 已有 |

**双板策略**：开发期在探索者上验证（收发器、屏、按键现成），装车换核心板（体积小）。代码同一套，只改引脚映射和 BSP 层。

> **核心板注意**：最小系统板**没有 CAN 收发器**，三块板各要外挂 SN65HVD230 模块（¥5×3）。
> **F407 核心板型号要确认**是 VET6（100 脚）还是 ZGT6（144 脚）——差 44 个引脚，引脚规划完全不同。

### 2.2 三条链路与断链行为

| 链路 | 传什么 | 频率 | 延迟 | 断了会怎样 |
|---|---|---|---|---|
| **CAN 1 Mbps 有线** | 目标速度、编码器、电压、故障码、UDS | 10–100 Hz | < 5 ms | 各节点自主安全停车 |
| **WiFi 2.4G** | 驾驶指令（50 Hz）+ 图像（5–8 fps） | 50 Hz / 5 fps | 30–130 ms | S3 心跳超时 200 ms 内限速停车 |
| **LoRa 62.5 kbps** | 遥测数字（1 Hz）+ 备份停车指令 + 车际意图 | 1–10 Hz | 与空中时间同量级 | 只影响遥测，不影响行车 |

**原则**：控制量永远走有线；无线只传"意图和画面"。

**PC 的两条腿**（不要混）：

```
主控：PC ──WiFi──→ S3 ──CAN──→ F407     （下发指令、看画面）
观测：PC ──USB-CAN──→ 总线              （抓包、注帧、发 UDS、扮演第二车）
```

WiFi 全断时，PC 仍可接总线看车在说什么——这是诊断仪的形态。

### 2.4 总线

- **车内**：CAN 1 Mbps，三块 MCU + PC 旁路，两端各一个 120 Ω 终端电阻
- **车际**：LoRa E22-400T22D（已有两块），改 62.5 kbps；只交换意图，不传控制量
- **网关存在的理由**：PC 说 TCP，总线说 CAN，中间必须有人翻译；且"人按下的摇杆"不能直接灌进动力域，必须先过校验、仲裁与超时保护——这就是 T-Box 的活

### 2.5 电源（原则：第一道保护在硬件上，不在 MCU 里）

- **硬件保护链（µs 级，不经过 MCU）**：电池 → 保险丝 → 防反接 PMOS → 硬件比较器（欠压 6.4 V / 过压 8.6 V / 过流）→ 主 MOS 双管并联 → 母线
- **分配**：7.4 V 直供电机驱动（不经开发板）；降压 5 V 供 S3 与 F407；**F103 由电池经独立降压单独供电**
- **独立供电**：电源域的 MCU 不与被保护母线共用电源，否则母线一塌，保护层自己也挂了
- **舵机单独供电**：DS3218 ×2 堵转可达 1.4 A，必须独立 5V/2A + 1000 µF 电容，不能从 S3 板取电
- **计量**：INA226（16 位、±0.1%、带库仑计）；**MCU 内部 ADC 不用于计量**
- **上电时序**：电池接入 → 比较器就绪（µs）→ MCU 启动（< 10 ms）→ 采样自检 → 分级上电（先核心层，200 ms 斜坡，再动力域）→ 允许动力域使能
- **保护不靠软件**：软件卡死、跑飞、重启时，硬件比较器照样切主 MOS；MCU 只负责记录、上报、以及"什么时候允许上电"

### 2.6 硬件结构：车板 + 三块自制板

**三块 MCU 全是现成核心板**（F407 核心板、F103C8T6 最小板、ESP32-S3-N16R8 开发板），都带向下 2.54 排针。所以它们**不用焊**，画三块小板，各装一个排母插座插上去。

**车板是机械底座**（亚克力或铝合金，300×220 mm），电路全在自制板上。

| 自制板 | 尺寸 | 上面插什么 | 板上还有什么 | 对应域 |
|---|---|---|---|---|
| **电源板** | 80×70 | F103 核心板 | 保险丝座、防反接 PMOS、主 MOS 双管、硬件比较器、INA226、DC-DC（7.4→5 V/3.3 V）、CAN 收发器 | 电源域 |
| **动力板** | 110×80 | F407 核心板 | DRV8871 ×4、电机端子 ×4、编码器端子 ×4、电流采样、CAN 收发器 | 动力域 |
| **主控板** | 90×70 | S3 核心板 | CAN 收发器、WiFi 天线座、USB 调试口、120 Ω 跳线 | 核心层 |

**驱动为什么放在动力板上**：PWM 到 DRV8871 只要 2 cm；而且电池 → 动力板 → 电机的大电流路径最短，不用把 8 A 送回底板再拉出来。

**为什么是三块板，不是一块大底板**：

1. **坏一块换一块**：调 F407 的时候不用动电源和 S3，换板子只要 4 颗螺丝。
2. **小板便宜**：三块都在 100×100 以内，打样 ¥5–30/款；一块 160×120 的大板要按面积算。
3. **域隔离落到物理上**：三个 MCU 不共电源平面和地平面，电机地的抖动进不到 F103 的 I²C 上。

**为什么平铺，不层叠**：

| 层叠的问题 | 后果 |
|---|---|
| 排针要贯穿三层 | CAN 和电源穿过 3 段桩线，加起来 60 cm+，1 Mbps 下开始见反射 |
| 拆装要全拆 | 调最下面那块，得把上面两块先拔掉 |
| 重心高、悬臂长 | 车一跑，顶层板跟着晃，排针接触电阻随机变化 |
| 车板本来够大 | 300×220 mm 平铺三块板只占一半，没必要叠 |

**车板分区（俯视）**

| 方位 | 放什么 |
|---|---|
| 后部左 | 电池组 4×18650 + 电源板 |
| 后部右 | 动力板（靠近后轮电机） |
| 中部 | 主控板（S3 + 天线，尽量远离大电流） |
| 前部 | 云台 + 摄像头、超声波 ×2 |
| 四角 | 520 电机 + 轮子 |

**CAN 总线拓扑**：三块板各挂一个收发器，双绞线串成一条链：电源板 → 动力板 → 主控板。物理最远的两端各插一个 120 Ω 跳线帽。

**板间线束：三组 + 电机线**

| 从 | 到 | 芯数 | 信号 | 接插件 |
|---|---|---|---|---|
| 电源板 | 动力板 | 4 | 7.4 V 主电源（2 芯粗）、CAN_H、CAN_L | XT30 + XH2.54-2 |
| 电源板 | 主控板 | 4 | 5 V、3.3 V（或 GND 回路）、CAN_H、CAN_L | XH2.54-4 带锁扣 |
| 动力板 | 主控板 | 2 | CAN_H、CAN_L | XH2.54-2 |
| 动力板 | 电机 | 4×2 + 4×4 | 电机相线（粗、≤15 cm）、编码器（细） | 凤凰端子 + XH2.54 |

> **验收标志**：如果发现自己在数第 8 根杜邦线，说明分层错了。三组线束 + 电机线，就这些。

**两条纪律**

- **CAN 终端**只在物理最远的两端插，中间那块拔掉。插三个终端 = 总线负载降到 40 Ω，通信会变脆。
- **走线**：CAN_H/CAN_L 全程双绞，与电机线分开 ≥5 cm（交叉时垂直）；大电流地与小信号地只在电源板入口单点相连。

**打样与成本**：三块板合计 ≈¥60–100（5 片，两层，都在 100×100 内）；元器件 ≈¥120–180（DRV8871 ×4、SN65HVD230 ×3、INA226、主 MOS、保险丝座、端子、排母）。

### 2.7 报文与总线契约（v1.0 暂定：按发送方分区）

**为什么按发送方分区**：一看 ID 就知道是谁发的，故障帧立刻能定位；而且优先级是"设计出来的"——CAN 仲裁 ID 越小越优先，`0x1xx`（控制量）排在 `0x4xx`（人想怎么开）前面，总线真挤的时候**先丢的是意图，不是控制**。

| ID | 发送方 | 内容 | 周期 |
|---|---|---|---|
| `0x100` | S3 | 目标速度 · 使能 · 档位 · 生效模式 · alive · CRC8 | 20 ms |
| `0x101` | S3 | 指令确认（生效模式 / 拒收原因） | 事件 |
| `0x150` | S3 | 路权意图（车际 / 虚拟节点） | 事件 |
| `0x200` | F407 | 实测转速 ×4 · 占空比 · 状态机 · 故障码 | 20 ms |
| `0x201` | F407 | 电机电流 · 温度 · 里程（可选） | 100 ms |
| `0x300` | F103 | 母线电压 · 电流 · SOC · 主 MOS 状态 · 保护位 | 100 ms |
| `0x400` | PC | 油门 · 刹车 · 方向盘 · 档位 · seq · CRC8 | 20 ms |
| `0x401` | PC | 云台 pan / tilt / 速度档 / 模式 | 100 ms |
| `0x7E0` / `0x7E8` | PC ↔ ECU | UDS 物理寻址 请求 / 响应 | 事件 |
| `0x7DF` | PC | UDS 功能寻址（广播刷写） | 事件 |

**总线负载账**：三路 50 Hz + 三路 10 Hz + 事件 ≈ **180 帧/s**；标准帧 8 字节最坏 130 bit（含位填充）→ 23.4 kbit/s → **1 Mbps 下占 2.3%**。

> 两个推论：①余量极大，100 Hz 反馈没必要上总线（留在 F407 内部）；②要做「70% 负载」实验必须人为灌帧，得灌到 **5385 帧/s**，同时确认 F407 在灌帧下 1 kHz 环仍不掉链子。

> **待拍板**：以上是方案 A。若选方案 B（保留 `0x210` 系列编号，只并掉 `0x211` 的两种含义），全表整体平移，接口逻辑不变。

### F0 细则：报文与判据

**为什么放 P0**：它是演示开场（人开着车进来），也是"总线是真主干"最直接的证明——指令走 CAN，不走 WiFi 直连。

**报文 `0x400 驾驶指令`**（PC → 总线），周期 50 Hz（20 ms），DLC=8：

| 字节 | 内容 | 说明 |
|---|---|---|
| 0 | 档位 + 模式 | 低 2 位档位（P/R/N/D），高 2 位模式（0 停 / 1 遥控 / 2 定速 / 3 自动） |
| 1 | 油门 | 0–100（百分比），对应目标加速度 0–800 mm/s² |
| 2 | 刹车 | 0–100，优先级高于油门（> 3% 时油门归零） |
| 3 | 方向盘 | int8，−100…+100，对应差速比 |
| 4 | seq | 每帧 +1，丢帧可被发现 |
| 5 | alive | 0–15 循环，判断发送方是否活着 |
| 6 | crc8 | 前 7 字节校验（poly 0x07） |
| 7 | 预留 | — |

> **真车手感的关键**：油门不是"目标速度"，是"目标加速度"。`v_ref += 油门 × a_max × (1 − v/v_max) × dt`，松油门走滑行阻尼，踩刹车优先。
> 这套东西的正式名字叫**线控底盘（Drive-by-Wire）**。

**验收判据（四条，缺一不算完成）**

1. `candump can0` 上稳定看到 0x400，50 Hz ±2 Hz，`seq` 连续无跳变。
2. 端到端延迟：摇杆动 → 轮子开始转 **< 50 ms**。
3. 发送端拔线：**200 ms 内自动停车**；插回 500 ms 内恢复。
4. 模式切换 遥控 → 定速：速度曲线**连续**，切换有握手（S3 回 `0x101 指令确认` 含生效模式，收到才切）。

### F5 细则：三层降级 + 三 MCU 互相看门狗

**Fail-safe 的正确定义**：不要求挂了还能跑，要求**挂了能停**。

| 层 | 触发条件 | 谁执行 | 现象 |
|---|---|---|---|
| ① 通信降级 | PC / WiFi 断，S3 仍活着 | S3 决策 + F407 执行 | 按距离缓 / 快 / 急停（见 F9 细则）+ 双闪 |
| ② 主控板失效 | S3 心跳丢失 200 ms | F407 本地 | 斜坡停 + 双闪 2 Hz + 蜂鸣 3 声 + 故障码 `0x05` |
| ③ 极端失效 | F407 也死 | **纯硬件** | 驱动使能脚下拉 → 电机断电 |

**必须补的漏洞**：F407 挂了，PWM 会停在最后占空比，车会一直跑。三个兜底都要做：

1. **驱动使能脚硬件下拉**（DRV8871 的 nSLEEP / TB6612 的 STBY 串电阻到 GND）——MCU 一死 GPIO 变高阻，驱动自动禁用，不依赖任何软件；
2. **F103 兜底**：300 ms 收不到 `0x200` → 切断动力域 5 V；
3. **F407 的 IWDG 复位后**靠第 1 条禁用。

于是形成「三 MCU 互相看门狗」：S3 看 F407、F103 看 F407、F407 看 S3、硬件看所有人。

### F9 细则：通信降级 —— 断网后按「还有多远」决定怎么停

这是三层降级里的**第 1 层**：PC 或 WiFi 断了，但 S3 活着、超声波还在，所以车不是"傻停"，是"看着距离停"。

**动态阈值（不是固定值）**

```
d_need = v² / (2·a_brake) + v·0.1s + 50mm
```

| 停车方式 | 减速度 | 纯制动距离 @300 mm/s | 含响应延迟 | 触发条件 |
|---|---|---|---|---|
| 缓停 | 800 mm/s² | 56 mm | 86 mm | `dist > 2·d_need` |
| 快停 | 2000 mm/s² | 22 mm | 52 mm | `d_need < dist < 2·d_need` |
| 急停 | 2500 mm/s²（短接制动） | 18 mm | 48 mm | `dist < d_need` 或测距失效 |

速度越快 `d_need` 越大，所以每 20 ms 重算一次；减速过程中若距离继续缩小，**自动升级**档位。

**三条硬规则**

1. **超声波超时 / 无效 = 前方有障碍** → 一律急停（保守优先，不是"没测到就是空的"）。单次测量要连续 3 次中 2 次一致才采信。
2. **急停 ≠ PWM=0**：PWM 归零电机还要滑 10–20 cm。要短接制动（IN1=IN2=1），但必须**先降到 100 mm/s 以下**再短接，否则大电流触发 OCP 烧驱动。
3. **恢复后不自动加速**：网络插回，车停在原地等复位，必须人重新给一次油门（真车叫"故障恢复后要求重新确认"）。

**谁决策、谁执行**

| 角色 | 感知 | 动作 |
|---|---|---|
| S3 | 有超声波 | 每 20 ms 算 `d_need`，发 `0x100` 模式=2 + 停车等级 |
| F407 | 无 | 收到模式=2 → 按指定减速度停；若 300 ms 连 `0x100` 都没有 → 自己**缓**坡停（它不知道前面有什么，缓一点更安全） |

**四个演示场景（验收判据）**

| # | 操作 | 期望现象 |
|---|---|---|
| 1 | 拔 WiFi，前方空旷 | 平滑减速，约 2 s 停 + 双闪 |
| 2 | 拔 WiFi，前方 200 mm 纸箱 | 明显快停，1 s 内停 |
| 3 | 拔 WiFi，前方 80 mm 纸箱 | 猛地停住（短接制动，车身点头） |
| 4 | 拔 WiFi + 手堵超声波 | 立即停（感知失效，保守处理） |

### F13 细则：OTA 分区与升级流程

**为什么值得做**：OTA 是车载 ECU 标配，也是 UDS 的另一半——F10 读数据，F13 写固件，共用 0x7E0/0x7E8。`D:\GitHub_Project\OTA` 里已有整套（Boot 16 KB + 固件头 + CRC + PC 下发脚本），**不需要重写，只需改造**。

**三处增量**

| 项 | 现在（OTA1） | 本项目 |
|---|---|---|
| 传输通道 | USART3 + ESP8266 AT 透传 | **CAN + UDS 0x34/0x36/0x37** |
| 分区模式 | 单 App 区 + 下载暂存区（搬运掉电变砖） | **A/B 双区**，写非运行区，写完切标志 |
| 版本可见 | 串口打印 | **UDS 0x22 读 DID** |

**分区表（F407ZE，512 KB）**

| 区 | 地址 | 大小 | 说明 |
|---|---|---|---|
| Bootloader | `0x08000000` | 16 KB | 选区 → 校验 → 跳转/回滚 |
| Slot A | `0x08004000` | 48 KB | 固件链接地址 A |
| Slot B | `0x08010000` | 48 KB | 固件链接地址 B |
| 参数/标志区 | `0x08060000` / `0x08070000` | 沿用 | 现有 `sys_flash` 不动，另加升级标志页 |
| 空闲 | `0x0801C000`–`0x0805FFFF` | ~280 KB | 留给字库/日志 |

**流程**：0x34 请求下载（地址+长度）→ 0x36 分块（每帧 6 字节）→ 0x37 结束 → 写非运行区 → CRC32 校验 → 写标志 → 复位 → Boot 校验新区 → 通过则切，不通过回旧区。

**时间预算**：48 KB ÷ 6 B = 8192 帧，1 Mbps 下约 1.1 s；加 3 扇区擦除，整体 **10 秒内**。

**验收判据（四条）**

1. 一条命令发起升级，10 秒内完成，重启后 `0x22` 读回版本变新。
2. **传输中途断电**，重新上电仍是旧版本可运行。
3. 下发 CRC 错位的固件，Boot 拒绝切换，报故障码，旧版本继续跑。
4. 升级前后参数区（里程、故障码）不被擦除。

**诚实边界**：车规 OTA 还要签名验签、差分升级、ISO 24089、升级中电源保障。本项目只做机制骨架，不做密码学，面试主动说明。

### F14 细则：智能功能当成「架构的论据」

**定位**：避障算法本身不值钱。它的价值只有两个：

1. 证明 OTA 真能"出厂后再长功能"——1.0 不避障，刷成 1.1 就会，刷回去又不会。
2. 证明域分工扛得住负载——算法跑在 **S3**，F407 只管 1 kHz 电机环。

**关键设计：智能功能必须跑在 S3 上，不许进 F407。** 这是"域隔离"的实证。

| 版本 | 内容 | 演示 |
|---|---|---|
| v1.0 | 遥控 + 定速 + 速度环 | 车能开，撞到就撞到 |
| v1.1 | F407 不变；**S3 新增**避障决策，通过 CAN 下发限速/停车 | 刷完自动躲障 |

**传感器**

| 件 | 数量 | 价格 | 用途 |
|---|---|---|---|
| HC-SR04 超声波 | 2–3 | ¥5/个 | 正前 + 左右，2–400 cm |
| TCRT5000 红外对管 | 5 | ¥8/组 | 巡线（可选，P2） |

**验收判据**

1. 300 mm/s 前进，正前 30 cm 有障碍，**减速并停在 15 cm 以外**。
2. 避障跑起来时，1 kHz 中断周期抖动 **仍 < 5 µs**（F407 翻转 GPIO 测）。
3. 把 S3 断电：200 ms 内停车，**F407 不重启**。
4. OTA 刷到 v1.1 避障生效；刷回 v1.0 消失。

**边界**：不做 SLAM，不做视觉识别，只做单目超声波阈值 + 状态机。

### F15 细则：感知链 —— 一个摄像头覆盖 270°

**定位**：不是为了"炫技"，是为了证明两件事：

1. **感知资源是可控的**——按需开、按场景调帧率，不和控制抢资源。
2. **一个摄像头覆盖 270°，比三个固定摄像头划算**——成本、布线、功耗都省。

**链路**

```
OV2640（DVP 8 位）→ S3 LCD_CAM → PSRAM 缓冲 → JPEG 编码 → WiFi TCP → PC（Qt 显示）
DS3218 舵机 ×2 ← S3 LEDC 50 Hz PWM ← 0x218 云台指令（来自 PC 或手持终端）
```

**为什么必须挂 S3，不能挂 F407**：F407 是动力域，DCMI + DMA 吃总线带宽，软件 JPEG 编码一帧 200–500 ms，会把 1 kHz 控制环拖抖。**动力域只做控制，不做图像。**

**云台规格**

| 轴 | 范围 | 说明 |
|---|---|---|
| 水平 pan | ±135°（270° 舵机） | 装限位块，**不做 360° 无限位**（线会缠断） |
| 垂直 tilt | −20° ~ +60° | 下看地面，上看远方 |

**报文 `0x218 云台指令`**，10 Hz，DLC=8：

| 字节 | 内容 |
|---|---|
| 0 | pan，int8，−135…+135 |
| 1 | tilt，int8，−20…+60 |
| 2 | 速度档（0 慢 / 1 中 / 2 快） |
| 3 | 模式（0 手动 / 1 自动扫描 / 2 归中） |
| 4–7 | 预留 + CRC8 |

**停稳再拍**（必须写进代码，否则图像全糊）：

```
收到 pan/tilt → 舵机转到目标角 → 等 250 ms 机械停稳
→ 采集 1 帧 → 编码 → 发送
→ 500 ms 内无新指令 → 降到 1 fps 预览
```

**验收判据（五条）**

1. 视频 5 fps 开时，F407 的 1 kHz 中断抖动**仍 < 5 µs**（动力域不受影响）。
2. 视频 5 fps 开时，CAN 转发延迟 **P99 < 3 ms**。
3. 视频 5 fps 开时，驾驶指令实测到达率 ≥ 18 Hz（20 Hz 下发，允许丢 2 帧）。
4. 拔掉摄像头：S3 不重启，只报故障码，视频流归零。
5. 云台转到目标后，**250 ms 内画面清晰**（停稳再拍生效）。

**边界**：不做视觉识别（OpenMV/K210 是另一个项目），不做 1080p（S3 无硬件 H.264），不做 360° 滑环。
